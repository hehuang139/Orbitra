# 主流模拟器平台特性吸收路线图

调研基线：2026-09-20。

本文关注模拟器前端与成熟单机模拟器的产品能力，不重复 [多平台路线图](multi-system.md) 中的主机接入计划。目标是把经过验证、适合浏览器和本地优先架构的能力逐步带入 Orbitra，而不是照搬其他项目的界面，也不因为上游核心具备某项功能就宣称 Orbitra 已经支持。

未勾选条目均未交付，阶段表示依赖和优先级，不承诺发布日期。每项能力只有通过本文的验收门槛后，才能加入 README 的“已实现功能”。

## 调研结论

| 参考项目    | 值得吸收的成熟能力                                                                                     | 对 Orbitra 的取舍                                                                            |
| ----------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| RetroArch   | 全局 / 核心 / 目录 / 游戏分层配置，按游戏保存输入和着色器预设，延迟调优，RetroAchievements，确定性联机 | 先实现可解释的配置继承和延迟测量；着色器、成就与联机必须按核心能力和设备性能开放             |
| ES-DE       | 元数据抓取与手工修正，自动 / 自定义合集，媒体浏览，按游戏选择模拟器，儿童 / 展示模式                   | 先做可撤销的元数据匹配和智能合集；远程图片、主题与外部服务必须显式选择并可清理               |
| Delta       | 适配移动端的统一核心接口，封面管理，分平台 / 分控制器映射，锁定与备份即时存档，同步历史，按键保持      | 延续现有统一会话接口；优先补齐快速继续、存档保护、同步历史和移动布局，不引入不可审计的皮肤包 |
| mGBA        | RTC、体感、震动、光照等硬件特性，补丁、作弊、录制、本地连接和可查看预览的即时存档                      | 先建立“核心能力注册表”，逐项暴露已验证能力；硬件 API 缺失时明确降级，不伪造兼容状态          |
| PPSSPP      | 按游戏配置、横竖屏独立触控布局、纹理增强、即时存档撤销、多人网络和运行时诊断                           | 吸收配置、布局和防误操作设计；高成本图形增强及网络能力先做性能与确定性原型                   |
| DuckStation | 控制器预设与按游戏配置、旋转、着色器链、补丁数据库、存档导入工具、成就和录制                           | 优先做配置与数据工具；社区数据库必须有版本、来源、许可证和关闭入口                           |
| EmulatorJS  | 浏览器内多核心加载、虚拟手柄、作弊与联机等 Web 集成能力                                                | 作为现有 FC / SFC 适配层的能力来源之一；Orbitra 仍需独立完成数据隔离、错误处理和跨浏览器验收 |

共同规律是：成熟平台把“游戏内容”“核心能力”“用户配置”和“存档数据”分层管理，并允许按游戏覆盖默认值。Orbitra 应先把这套基础补齐，再扩展容易造成数据损坏、不同步或联机分歧的高级功能。

## 阶段 0：能力契约与可测基线（P0）

- [x] 扩展平台注册表和模拟器会话接口，为即时存档、倒带、补丁、作弊、着色器、录制、多人、RTC、体感、震动、麦克风等能力提供显式标志；界面只展示当前核心真实实现并通过验收的功能。
- [ ] 建立“全局 -> 平台 -> 游戏”的配置继承模型，保存值时只记录相对上一级的差异，并提供查看来源、恢复平台默认和恢复全局默认的操作。
- [x] 为每个核心记录精确版本、构建校验值、状态格式版本和能力矩阵；核心升级前必须给出即时存档兼容结论和回滚方案。
- [ ] 建立本地性能基线，记录冷启动 / 热启动到首帧、输入到画面、音频欠载、帧时间、内存峰值与倒带增长；默认不上传遥测。
- [x] 把功能状态统一为“计划、实验、已验证、不可用”，不可用时显示具体原因，例如浏览器 API、核心能力、资源或性能不足。

验收：现有五个平台的功能入口均由能力注册表驱动；关闭或缺失能力不会留下无效按钮。测试能够检测核心版本、配置继承、状态迁移和不受支持能力的降级路径。

## 阶段 1：启动与连续游玩（P0）

- [x] 在游戏库提供“继续上次游戏”，同时显示平台、最后游玩时间、最新自动存档时间和将要使用的核心；游戏或存档缺失时回到可修复流程。
- [ ] 启动前提供“继续自动存档 / 正常启动 / 选择即时存档”，记住每个游戏的选择；任何失败都不能覆盖最后一个可用自动存档。
- [ ] 把启动过程拆成资源检查、核心加载、ROM 装载、存档恢复、首帧与音频就绪等可观察阶段，支持取消、重试和复制诊断信息。
- [ ] 记录未正常结束的会话并在下次打开时提供恢复；恢复失败时保留原状态并允许正常启动。
- [ ] 从最近游戏、收藏、搜索结果和 PWA 快捷入口进入时复用同一启动流程，避免出现不同入口采用不同存档或配置的情况。
- [ ] 在不改变模拟结果的前提下缓存已校验的核心资源和游戏元数据；以阶段 0 的基线为准，首帧时间不得出现未解释的明显回退。

验收：冷启动、热启动、离线、损坏存档、核心资源缺失、恢复失败和用户取消均有自动化覆盖；刷新或崩溃模拟后可以恢复，且不会静默丢失或覆盖进度。

## 阶段 2：按游戏配置、输入与画面（P1）

- [ ] 支持按平台和按游戏覆盖画面风格、缩放、旋转、音量、速度、自动保存、倒带预算及适用的核心选项，并明确显示继承来源。
- [ ] 将输入配置扩展为“设备 -> 平台 -> 游戏”覆盖；加入可选的按键保持、连发和快捷动作映射，避免与浏览器及辅助技术快捷键冲突。
- [ ] 分别保存手机横屏与竖屏触控布局，允许在安全区内移动和缩放控件，并提供一键恢复当前平台默认布局。
- [ ] 建立少量随应用分发、许可证清晰的画面预设，包括整数缩放、LCD / CRT 和竖屏旋转；实时预览资源开销，Canvas 2D 降级时只保留可实现选项。
- [ ] 增加延迟诊断视图，展示刷新率、帧时间、音频缓冲和当前降级项；runahead、frame delay 等方案只有在核心确定性和目标设备预算通过后才进入实验状态。

验收：配置导出 / 恢复包含新增覆盖层，旧偏好能够迁移；键盘、标准与非标准手柄、触屏在旋转、断连、后台切换后不会残留按键。低性能设备不会因默认开启增强效果而变差。

## 阶段 3：游戏库与存档安全（P1）

- [ ] 以 ROM 内容哈希、平台和地区信息进行可撤销的元数据匹配，支持手工修改标题、封面、地区、发行信息与标签；远程抓取默认关闭并展示来源。
- [ ] 增加“最近游玩、从未启动、最近导入、已完成、平台、标签”等智能合集，以及不复制 ROM 的自定义合集。
- [ ] 支持锁定重要即时存档、为自动存档保留有限历史，以及在覆盖 / 删除后立即撤销；清理策略不得删除锁定项或唯一可恢复进度。
- [ ] 为账号同步增加版本历史与设备来源，冲突时允许逐项保留本机、远端或两者；离线操作重新联网后不得静默覆盖较新的进度。
- [ ] 提供存储健康检查，识别孤立封面、无 ROM 的记录、不可读取的状态和版本不兼容数据，并在用户确认后清理。

验收：元数据服务不可用时游戏库仍完整可用；批量抓取、合集、撤销、历史恢复和同步冲突均有确定性测试。外部图片和元数据可单独清除，不影响 ROM 与存档。

## 阶段 4：模拟增强与内容工具（P2）

- [ ] 支持 IPS、UPS、BPS 等补丁的本地临时应用，保存原 ROM 哈希、补丁哈希和结果哈希；默认不改写原 ROM，失败时可完整回滚。
- [ ] 按平台与核心实现作弊码导入、校验、启停和分组，保存格式与来源；启动“安全模式”时一键禁用全部作弊和实验选项。
- [ ] 逐项验证并接入 mGBA 上游具备、但当前网页适配层尚未确认或暴露的 RTC、体感、光照、震动等能力；权限被拒绝或设备缺失时提供可预测的替代输入或明确不支持。
- [ ] 评估原始画面 / 处理后画面截图、短视频或 GIF 录制；设置时长与内存上限，录制失败不得影响模拟和存档。
- [ ] 只有在同一平台存在两个经过维护、许可证兼容且状态策略明确的网页核心时，才开放按游戏选择核心；切换前展示即时存档不兼容风险。

验收：补丁、作弊和核心切换都不修改用户原始 ROM；备份格式记录新增数据的版本和来源。每项硬件能力至少有支持、拒绝权限、设备缺失和核心不支持四条路径。

## 阶段 5：可选在线能力（P2，独立评审）

- [ ] 评估 RetroAchievements 的浏览器集成，采用显式登录和最小权限令牌存储；区分普通与 hardcore 模式，并在后者中可靠禁用即时存档、倒带、慢速和作弊。
- [ ] 先实现同机双人及独立控制器映射，再为确定性核心制作联机原型；握手必须校验应用、核心、ROM、补丁和配置哈希。
- [ ] 区分本地多人同步、掌机连接线、平台原生网络三种模型，不把其中一种的成功推导成另外两种已支持。
- [ ] 评估 WebRTC 直连与可选中继，清楚展示房主、延迟、断线和隐私状态；不得自动上传 ROM、存档或账号凭据。
- [ ] 为旁观、重连和不同步提供可复现诊断；任何自动回滚都先保护本地持久化存档。

验收：在线功能完全可选，关闭后不发起第三方请求；协议不匹配在启动前被拒绝。至少完成跨两个受支持浏览器的长时间会话、断网重连、不同步检测和恶意输入边界测试后，才能移出实验状态。

## 不直接照搬的能力

- 不建立自动下载 ROM、BIOS、固件、密钥、作弊库或补丁包的入口；外部数据库必须先审查许可证、完整性和更新策略。
- 不引入无边界的主题或控制器皮肤市场。自定义资源需要格式版本、尺寸 / 数量限制、内容安全策略和删除入口。
- 不默认启用高成本着色器、纹理增强、runahead 或录制；浏览器内存、耗电和热降频是正式验收的一部分。
- 不以云同步代替本地备份，也不以在线账号作为启动游戏的前提。
- 不复用许可证不兼容项目的实现代码；本文只借鉴公开的产品能力，具体实现继续遵循本仓库与所用核心许可证。

## 统一交付门槛

每个阶段的实现 PR 都应同时提供：

- 能力注册、数据格式和迁移说明，包含回滚与旧版本行为。
- 单元测试以及覆盖导入、启动、游玩、保存、刷新恢复和失败路径的浏览器测试。
- Chromium、Firefox、Safari / WebKit 与至少一台移动设备的结果；尚未验证的环境保持“未验证”。
- 键盘、手柄和适用触屏流程，以及焦点、动态状态提示和减少动画设置的可访问性检查。
- 离线行为、存储配额、内存峰值、资源释放和核心切换回归。
- 第三方服务、素材、协议与代码的许可证、隐私、故障降级和移除方案。
