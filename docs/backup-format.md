# 游戏库备份格式 v1

应用通过侧栏「备份与恢复」导出普通 ZIP。默认仅含所选游戏的元数据、电池存档和即时存档；包含 ROM 必须显式选择。没有账号、云同步或加密，用户设置不在此包内。Orbitra 为兼容更名前的数据，继续使用 `advance-gba` 数据库版本 1。

## 清单与文件

ZIP 根目录只有 `manifest.json`，其余条目只允许以下路径：

```text
games/<游戏内容 ID>/rom.<gba|gb|gbc>
games/<游戏内容 ID>/battery.sav
games/<游戏内容 ID>/state-<0..5>.bin
```

清单包含 `format: "advance-gba-backup"`、`formatVersion: 1`、ISO UTC `exportedAt`、`coreVersion`、`games` 和 `files`。每个游戏包含现有 `Game` 元数据（包括 `platform`）、可选 `rom` / `battery` 文件路径、`states` 数组；即时存档记录游戏 ID、槽位、创建时间、可选 PNG data URL 截图、可选核心标识和 `path`。ROM 负载名必须与平台严格对应，使用 `rom.gba`、`rom.gb`、`rom.gbc`、`rom.nes`、`rom.sfc` 或 `rom.smc`。`files` 为所有负载记录 `path`、`size` 和原始负载的十六进制 SHA-256。清单自身不列入文件校验表，ZIP CRC 检查覆盖它。

为兼容已有数据库，GBA 游戏 ID 仍为 `SHA-256(ROM)`。GB 与 GBC 使用平台域分隔的 ID：`SHA-256(UTF-8("advance-game-id:v1\0<platform>\0") || SHA-256(ROM))`，其中内层摘要按 32 个原始字节拼接。这样同一组 ROM 字节以 GB 与 GBC 身份导入时不会共享游戏和存档，结果仍是 64 位小写十六进制 ID。文件名扩展、`platform` 和 ROM 负载扩展必须一致。

格式版本保持 v1。旧版 v1 清单没有 `platform` 时，仅文件名为 `.gba` 的记录会明确迁移为 `gba`，并继续使用原有内容 ID 和 `rom.gba` 路径；缺少平台的 `.gb` / `.gbc` 记录不会被推断。新导出始终写入平台。不含 ROM 时只能匹配本地或用户临时提供的相同平台、扩展名、大小和内容 ID；文件名和标题仅用于显示，不作为解压路径。

## 大小与解析边界

| 项目                                               | 上限                                                                                                     |
| -------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| ZIP 文件                                           | 72 MiB                                                                                                   |
| 解压后全部条目（含清单）                           | 64 MiB                                                                                                   |
| 所选游戏的关联 ROM、存档与清单合计（含省略的 ROM） | 64 MiB                                                                                                   |
| 游戏 / 文件数                                      | 16 / 129                                                                                                 |
| 单 ROM                                             | GBA：192 字节至 32 MiB；GB / GBC：32 KiB 至 8 MiB；NES：16 KiB + 16 字节至 8 MiB；SNES：32 KiB 至 16 MiB |
| 单即时存档 / 电池存档                              | 16 MiB / 1 MiB                                                                                           |
| 清单 / 单截图 data URL                             | 2 MiB / 256 KiB 字符                                                                                     |

这是当前内存实现的保守软件边界，不代表低性能设备已验收。ZIP 只接受 stored / deflate；拒绝 ZIP64、分卷、加密、重复条目、未知路径、路径穿越、重叠条目、未声明负载、缺失或交叉引用、平台 / 文件扩展 / ROM 负载路径错配、声明大小不符和校验失败。按小块解压，实际输出超过声明时立即中断。损坏文件不会进入写事务，未知版本也不会尝试降级解释。

## 导出与恢复语义

为保证省略 ROM 的包仍能在当前恢复实现中处理，分批边界也计入关联 ROM 的声明大小。例如三款 32 MiB 游戏即使不包含 ROM，也需要分批备份。导出和只读解析使用相同校验；此限制可在以后采用流式恢复时重新评估。

打开面板先暂停当前游戏、排空后台写入并显式捕获最新 SRAM。捕获失败会报错，不会声称已包含最新进度。随后四个 IndexedDB 表在同一只读事务中取得导出快照。面板期间游戏保持暂停；关闭后可手动继续。

解析、解压和哈希均在持久化写入之前完成。预览展示本地冲突、缺 ROM 和核心来源；默认保留已有元数据、电池存档和每个槽位，可分别选择使用备份。新游戏必须同时恢复元数据，缺少 ROM 时不能提交该游戏。取消预览不写数据库。

新创建的即时存档记录当前平台所用核心的稳定版本及资源 SHA-256。旧存档没有此信息，来源保持未知。未知或不同核心的即时存档默认跳过，用户显式选择前可查看提示；电池存档独立选择。这里不承诺不同核心之间的即时存档兼容性。

只恢复电池存档而保留旧自动槽 0 时，会在同一事务设置游戏元数据的可选 `skipAutoState: true`。下次启动（包括刷新后）从电池进度开始，旧即时档仍可手动读取，避免自动加载旧槽覆盖恢复的电池进度。生成新的槽 0 时，存档和标记清除一起提交。此字段随游戏元数据备份；旧包没有该字段时采用正常自动续玩规则。

恢复先检查预览对应的本地内容指纹，再在一个四表写事务中重新比较原始内容，避免异步校验期间的修改被覆盖。所有选中项目一起提交；请求失败、配额不足或事务中断时全部回滚。预览过期时需要重新预览。成功后销毁旧运行实例，重新启动游戏从恢复后的数据库读取进度。

站点用量和配额仅是浏览器估计，未知值不阻止操作。即使估计足够，实际写入仍可能失败，最终由数据库事务回滚保护。实体设备、内存峰值和跨浏览器验收继续在 [v1.2 roadmap](roadmaps/v1.2.md) 与 [兼容性矩阵](compatibility-matrix.md) 记录。

不含 ROM 的导出只读取 ROM 键，不复制 ROM 负载；整理计数使用 `count/getKey`。需要读取 ROM 的快照和恢复先检查游戏数与声明大小，再读取负载。解压、快照和事务比较仍可能同时持有多份数据，64 MiB 上限不等于浏览器实际内存峰值。
